## Phase 0 — 최종 점검 (Opus, 필수, 15~20분)

### 무엇을 하나
Phase A~C 착수 전에, 이 계획 문서(requirements.md·structure.md) 자체에 구멍이 없는지 **Opus 모델로 전환해서** 한 번 검토받는다. 소넷이 짠 계획을 소넷이 그대로 실행하면 같은 사각지대를 못 보고 넘어갈 수 있어서, 판단력이 필요한 계획 검토 단계만 별도 모델로 교차 확인.

### 절차
1. Claude Code에서 모델을 Opus로 전환 (`/model` 명령 또는 상단 모델 선택).
2. 이 두 파일(`requirements.md`, `structure.md`)을 열어달라고 하고, 다음을 구체적으로 물어본다:
   - 우선순위 순서(테스트 → 리팩토링)가 맞는지
   - Phase C의 "1.5초 자동 백업과 분리" 설계가 정말 안전한지, 놓친 예외 상황은 없는지
   - 목요일 하루 시간 배분이 현실적인지(과소/과대 산정 여부)
   - 수용 기준이 "완료"를 판단하기에 충분히 구체적인지
3. 지적 사항이 있으면 이 문서를 그 자리에서 갱신.
4. 점검 끝나면 다시 소넷으로 돌아와 Phase A부터 실행 (실행은 소넷으로 충분 — 판단이 필요한 계획 검토만 Opus 역할).

### 왜 이렇게 하나
계획을 짠 모델이 스스로 검토하면 같은 맹점을 반복할 위험이 있다는 게 사용자 판단. 비용이 큰 작업은 아니라서(15~20분) 착수 전 한 번의 교차 검증으로 얻는 안전성이 비용보다 큼.

## Phase A — 참고문헌 파서 테스트 (필수, 2~3시간)

### 무엇을 하나
`refparser.js`(문장→칸으로 분해)와 `refassembler.js`(칸→APA 문장으로 재조립) 두 파일은 화면(DOM)을 전혀 안 쓰는 순수 함수라, Node.js로 바로 실행해서 "입력 → 예상 출력"을 비교하는 테스트를 짤 수 있다.

### 절차
1. `연구노트앱/docsPlan/참고문헌-파서/규정.md`을 다시 훑어 지금까지 정해진 규칙(저자 표기·이탤릭·저자 수 규칙 등) 전수 확인.
2. 실제 사용자가 논문 폴더에서 써온 원문 사례 중 대표적인 것들을 모은다 — 정상 케이스(학위논문/학술지/단행본/번역서/책의 한 장/웹자료) + 오늘 겪은 것 같은 비정상 원문(줄바꿈 공백 낀 것 등).
3. `연구노트앱/refparser.test.js`(가칭) 신설 — Node 내장 `assert` + `node:test` 모듈만 사용(별도 설치 불필요, 이 프로젝트 컨벤션인 "가벼운 도구" 원칙과 맞음).
4. 테스트 실행: `node --test refparser.test.js` 한 줄이면 끝나게 구성.
5. 실행 결과를 한국어로 요약해서 보여주는 안내(통과 N개 · 실패 N개) 추가 — 사용자가 비개발자이므로 Node 기본 출력(영어 스택트레이스)만 보여주지 않는다.

### 예상 문제점 & 보완책
| 문제점 | 왜 생기나 | 보완책 | 보완책 효율성 |
|---|---|---|---|
| 테스트 쓰다가 "몰랐던 사각지대"가 더 나옴 (오늘 건 말고 또 다른 정규식 구멍) | 20개 넘게 실제 사례를 넣다 보면 필연적으로 나옴 | 그 자리에서 다 고치려 하지 말고, **발견 즉시 별도 목록(`known-issues.md`)에 적어두고 테스트는 "현재는 실패함"으로 표시(skip 처리)** — 목요일 하루 분량이 무한정 늘어나는 걸 막음 | 높음 — 범위가 커지는 걸 막는 가장 간단하고 확실한 방법 |
| 정규식을 고치다 다른 정상 케이스를 깨뜨림 (회귀) | 정규식은 서로 얽혀 있어서 한 곳을 넓히면 다른 곳이 과하게 매칭될 수 있음 | 정규식 하나 고칠 때마다 **전체 테스트를 다시 돌려서 기존 테스트가 다 통과하는지 확인 후 다음으로 진행** (한 번에 여러 개 안 고치기) | 높음 — 테스트를 만드는 이유 자체가 이 문제 방지임 |
| 실제 사례가 부족해서 테스트가 형식적으로만 채워짐 | 사용자가 그동안 겪은 오탈자 사례를 기억으로만 모으면 놓치는 게 많음 | 참고문헌 화면의 "손 안 댐"으로 남은 항목들을 실제로 열어서 원문을 몇 개 가져와 테스트 소재로 씀 (이미 있는 데이터 재활용) | 중간 — 실데이터 기반이라 품질은 좋지만 사용자가 화면을 열어 확인해줘야 해서 5~10분 정도 사용자 개입 필요 |

### 완료 확인 방법
`node --test refparser.test.js` 실행 → 통과/실패 개수를 한국어로 보고. 실패가 남아있다면 known-issues.md로 옮기고 왜 남겨뒀는지 한 줄 설명.

## Phase B — PDF 백업 습관 안내 (필수, 10분)

### 무엇을 하나
도움말 §7(저장·백업·동기화)에 "PDF는 논문 폴더 한 곳뿐"이라는 기존 경고 옆에, 정기적으로 그 폴더 자체를 외장하드/구글드라이브 등에 복사해두라는 실천 안내를 한 줄 추가.

### 절차
1. `index.html` §7 문구 옆에 안내 추가 (이미 있는 경고 문장 바로 아래, 오늘 세션에서 추가한 "완전 삭제" 안내와 같은 자리).
2. `?v=` 버전 태그는 이번엔 CSS/JS 변경이 없으니 갱신 불필요 (index.html 자체 텍스트라 새로고침만으로 반영).
3. 세이브 + GitHub 올리기.

### 예상 문제점 & 보완책
| 문제점 | 보완책 |
|---|---|
| 안내만 있고 실제로 실천 안 하면 무용지물 | Phase C(자동화)로 이어지면 이 문제 자체가 해소됨 — B는 "최소한의 안전장치", C는 "진짜 해결책"으로 역할 분담 |

## Phase C — PDF 백업 자동화 (여유분, 2~3시간)

### 무엇을 하나
「백업」 버튼을 누르면 지금은 글자 데이터(메모·발췌 등)만 백업 폴더로 복사되는데, 여기에 논문 폴더의 PDF도 함께 복사되는 옵션을 추가.

### 절차
1. `pickBackupDir()`(readwrite 권한, `app.js:7341` 부근)와 `paperDirHandle`(read 권한, `app.js:7191`)을 둘 다 이미 갖고 있으니, 백업 시점에 `paperDirHandle.values()`로 PDF 목록을 순회하며 `backupDirHandle`에 없는 파일만 복사.
2. UI: 백업 버튼 옆에 "PDF도 포함" 체크박스(기본 꺼짐 — 용량 문제 때문에 사용자가 선택하게).

### 예상 문제점 & 보완책
| 문제점 | 왜 생기나 | 보완책 | 효율성 |
|---|---|---|---|
| 자동 백업이 1.5초마다 도는데, 그때마다 PDF 전체를 다시 복사하면 디스크 I/O가 크게 늘고 노트북이 버벅일 수 있음 | 지금 자동 백업은 "저장 1.5초 뒤"마다 도는 가벼운 텍스트 저장용으로 설계됨 — PDF 같은 큰 파일 복사는 이 주기에 안 맞음 | **PDF 복사는 자동 백업(1.5초 주기)에서 완전히 분리** — 「백업」 버튼을 수동으로 눌렀을 때만, 그리고 **이미 백업 폴더에 같은 이름 파일이 있으면 건너뛰기**(새 논문만 복사) | 높음 — 문제의 원인(주기)과 분리하는 게 가장 확실 |
| 백업 폴더 용량이 논문 폴더만큼 두 배로 늘어남 | PDF를 통째로 복사하는 방식이라 당연히 생기는 트레이드오프 | 기능을 기본값 "꺼짐"으로 두고, 켜기 전에 "논문 폴더와 같은 용량이 더 필요합니다" 안내 문구를 보여줌 | 중간 — 근본적으로 없앨 수 없는 트레이드오프라 안내로 사용자 판단에 맡기는 게 최선 |
| 논문 폴더에 파일이 많으면(수백 개) 처음 켤 때 복사가 오래 걸림 | 최초 1회는 전체 복사가 불가피 | 진행률 표시(토스트 메시지로 "N/M개 복사 중") | 낮음~중간 — 편의 기능이라 없어도 동작엔 문제없음, 여유 되면 추가 |

### 완료 확인 방법
백업 폴더를 탐색기로 직접 열어서 PDF가 실제로 들어갔는지, 두 번째 백업 시 새 파일만 늘었는지(중복 복사 안 됐는지) 확인.

## 목요일 시간 배분 (제안)
1. Phase A — 2~3시간 (오전 또는 집중 가능한 시간대)
2. Phase B — 10분 (A 끝나고 바로)
3. 시간·컨디션 남으면 Phase C 착수, 안 되면 다음 세션으로 이월 (이 문서에 이미 절차가 적혀 있으니 이어서 하면 됨)

## 롤백 계획
각 Phase는 별도 커밋으로 나눠서 세이브 — 문제가 생기면 그 Phase의 세이브만 되돌리면 됨(다른 Phase에 영향 없음). Phase C는 새 기능이라 기본값을 "꺼짐"으로 둬서, 문제가 생겨도 기존 백업 흐름(텍스트만)은 그대로 유지됨.
